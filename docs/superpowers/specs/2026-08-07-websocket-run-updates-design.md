# WebSocket 运行更新设计

## 目标

通过 WebSocket 让运行详情页自动反映任务执行、审批和反馈变化；为后续工作台任务列表实时更新建立同一套按仓库分组的事件机制。

## 范围与阶段

### 第一阶段：运行详情页

- 页面 `/ui/runs/{run_id}` 连接该运行的 WebSocket 频道。
- 运行状态、轮次、动作、审批、反馈或最终结果变化后，服务端发布运行更新事件。
- 客户端收到事件后重新加载当前详情页，展示服务端最新 HTML；不维护复杂的浏览器端状态。
- 连接关闭或失败时采用带退避的自动重连；WebSocket 不可用时页面保持可手动刷新。

### 第二阶段：工作台

- 工作台连接当前仓库的事件频道。
- 新建任务、开始运行、运行状态变化及审批变化发布仓库更新事件。
- 收到事件后重新加载工作台，使左侧任务列表和“当前运行”卡片同步更新。

## 架构

- 新增进程内 `WebUIEventHub`：以仓库路径和运行 ID 维护订阅队列。
- `CoreService`、`AgentRunner` 与 WebUI 路由在写入可见运行状态后发布事件；同步 runner 的工作线程通过事件循环安全地将消息投递给 WebSocket 协程。
- 新增 WebSocket 路由：`/ui/ws/runs/{run_id}` 与 `/ui/ws/workbench`。连接只接收服务端推送，不接收业务指令。
- 事件只作为“刷新提示”，数据仍由原有 HTML/HTTP 路由读取；事件负载包含事件类型、仓库标识、运行 ID 和时间戳，但不包含任务文本、动作参数或密钥。
- 首版仅支持单个 FastAPI 进程；不引入 Redis 或跨进程广播。

## 安全与一致性

- 详情连接必须先验证该运行存在并且属于当前选择的仓库；未知运行直接关闭。
- 工作台连接仅订阅当前仓库的频道。
- 每次状态变化允许合并为一次刷新提示；丢失单个事件不影响最终一致性，因为刷新会读取持久化状态。
- 客户端避免并发刷新：页面正在重新加载时不再处理后续事件。

## 验收标准

- 对运行详情页建立 WebSocket 连接后，运行状态或审批变化会触发刷新提示。
- 详情页脚本创建连接、在关闭后重连，并在收到有效事件时重新加载。
- 事件中心不泄露动作参数、上下文内容或敏感字段。
- 现有非 WebSocket 页面行为和 API 保持不变。
- 为工作台频道提供服务端订阅与发布接口，第二阶段可直接接入页面脚本。
