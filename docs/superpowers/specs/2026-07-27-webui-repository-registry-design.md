# WebUI 仓库注册与切换设计

## 目标

让 Harness WebUI 在应用级目录持久保存已注册的仓库，并允许用户在工作台添加、选择和切换仓库。每个仓库继续使用其自身的 `.harness` 存储，任务与运行记录不跨仓库混合。

## 范围

- 注册一个存在的本地目录，保存其规范化绝对路径。
- 在应用级目录保存注册列表与当前选中仓库。
- 在 WebUI 侧栏展示全部注册仓库及其显示名称，并明确标识当前仓库。
- 通过 WebUI 选择已注册仓库；选择后刷新至该仓库的工作台。
- 重命名注册仓库的显示名称，不修改本地目录名或 Git 仓库名。
- 删除注册仓库，仅从应用级注册表取消注册，不删除磁盘目录、`.git` 或 `.harness` 数据。
- 新建任务、运行详情和审批操作均使用当前选中仓库的 `CoreService`。
- 为首次启动自动注册传入的默认仓库，使既有 `create_app(CoreService(...))` 用法保持可用。
- 拒绝不存在的路径、非目录路径与重复注册；错误以 HTTP 400 返回。

## 非目标

- 不实现本地目录或 Git 仓库的重命名、删除或排序。
- 不改变 CLI 与 API 现有的显式 `--repo` / `repo_path` 语义。
- 不在不同仓库之间共享任务、运行、记忆或 `.harness` 数据。

## 架构

新增一个小型 `RepositoryRegistry`，只负责应用级 JSON 文件的读取、原子写入、路径规范化和当前仓库选择。默认文件位置基于平台的用户配置目录；测试可显式传入临时目录，避免触及真实用户配置。

WebUI 保持一个仓库路径到 `CoreService` 的内存缓存。路由在每个请求开始时从注册表读取当前仓库，再取得对应服务。每个服务自行初始化目标仓库下的 `.harness` 目录，因此原有存储隔离边界不变。

## 数据格式

注册表 JSON 为：

```json
{
  "repositories": [
    {"id": "project-a", "path": "C:/work/project-a", "name": "项目 A"},
    {"id": "project-b", "path": "C:/work/project-b", "name": "项目 B"}
  ],
  "current_repository": "C:/work/project-a"
}
```

仓库路径按解析后的绝对路径去重。首次注册时，目录名作为默认显示名称并设为当前仓库。重命名只更新 `name`。删除当前仓库时，自动选择剩余列表中的第一个仓库；删除最后一个仓库时，注册表没有当前仓库，工作台显示添加仓库提示。

## WebUI 交互与路由

- `GET /` 与 `GET /ui` 渲染注册仓库列表和当前仓库内容。
- `POST /ui/repositories` 接收 `{"path": "..."}`，注册目录并将其设为当前仓库。
- `POST /ui/repositories/{repository_id}/select` 选择已注册仓库并以 303 跳转至工作台。
- `POST /ui/repositories/{repository_id}/rename` 接收 `{"name": "..."}`，更新显示名称。
- `POST /ui/repositories/{repository_id}/delete` 取消注册并以 303 跳转至工作台；此路由不会删除任何本地文件。
- 原有任务、运行和审批路由在当前仓库服务上执行。
- 运行详情按当前仓库查找；跨仓库的运行 ID 不会泄露或被访问。

## 错误处理

- 空路径、缺失路径、文件路径、空显示名称与未注册的操作目标返回明确的 400/404 错误。
- 损坏的注册表 JSON 不被静默覆盖：服务启动或请求时返回可诊断错误，保护用户已有配置。
- 写入先写临时文件再替换原文件，避免中断导致半份 JSON。

## 测试

测试覆盖注册、重复处理、选择、重命名、删除当前仓库、重启后的持久化、无效路径，以及 WebUI 切换后任务仅显示在对应仓库。测试通过临时应用级配置目录隔离真实环境，并使用既有 FastAPI 路由调用辅助方法。
